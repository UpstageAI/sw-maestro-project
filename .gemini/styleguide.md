# Repository Review Style Guide

이 문서는 저장소 템플릿에서 사용할 **Gemini 리뷰 기준**을 정의한다.
리뷰어는 아래 규칙을 기준으로 PR, 문서, 설정 변경을 검토한다.

---

## Review Comment Style & Language

- 모든 리뷰 코멘트는 **한국어로 작성한다.**
- **무엇이 어긋났는지**, **왜 문제인지**, **어떻게 맞추면 되는지**를 함께 제시한다.
- 사소한 제안에는 `[nit]` 접두어를 붙여 구분한다.
- 리뷰에서는 **범위 통제**, **문서 간 동기화**, **규칙 정합성**, **예시 정확성**을 우선 검증한다.

---

## 1) 레포 기본 전제

다음 전제는 저장소 전반에서 일관되게 유지되어야 한다.

- 이 문서는 특정 서비스가 아니라 **일반적인 저장소 템플릿 기준**을 다룬다.
- 프로젝트 고유 규칙이 있다면 README, 아키텍처 문서, 운영 문서 중 하나에 **정식 기준 문서**로 명시되어 있어야 한다.
- 예시, 용어, 링크, 자동화 규칙은 서로 충돌하면 안 된다.
- 보안상 민감한 값, 실제 비밀 정보, 실제 운영 키는 문서와 예시에 포함하지 않는다.

### 리뷰 체크포인트

| 검사 항목 | 규칙 |
|---|---|
| 범위 일치 | 다른 프로젝트 문맥이나 불필요한 도메인 예시가 섞이면 안 된다. |
| 기준 문서 | README, 설계 문서, 운영 문서 사이의 규칙이 충돌하면 안 된다. |
| 예시 정합성 | 명령어, URL, 심볼, 파일 경로 예시가 문서마다 다르게 적히면 안 된다. |
| 보안 | 실제 키, 비밀번호, 민감한 토큰, 운영 URL이 예시에 포함되면 안 된다. |

## 2) 주요 문서와 기대 역할

리뷰 시 문서의 위치와 역할을 먼저 파악하고, 해당 문서가 담당해야 할 정보만 담고 있는지 확인한다.

| 파일명 | 핵심 역할 | 주요 독자 |
|---|---|---|
| `README.md` | 저장소 진입점, 사용법, 공통 규칙 | 전원 |
| `SPEC.md` | 요구사항과 범위 정의 | 기획, 개발 |
| `ARCHITECTURE.md` | 구조, 책임 경계, 데이터 흐름 | 개발 |
| `AI.md` | AI/Agent 관련 설계와 제약 | AI, 개발 |
| `TEST_AND_DEMO.md` | 테스트 체크리스트와 데모 흐름 | 전원 |
| `ref/*.md` | 참조 규칙, 협업 규칙, 정책 문서 | 전원 |
| `feedback/*.md` | 기준 문서에 대한 리뷰/비판/개선 제안 기록 | 작성자, 리뷰어 |

### 리뷰 원칙

- 문서는 자신의 역할에 맞는 정보만 담아야 한다.
- 다른 문서가 이미 기준을 정의한 경우, 복제하기보다 **참조 관계를 명확히 유지**해야 한다.
- 같은 개념을 여러 문서에서 설명할 때는 용어와 예시가 동일해야 한다.
- `feedback/*.md` 문서는 기준 문서를 대체하지 않는 **2차 리뷰 문서**로 취급한다.

## 3) 제목, 섹션, 구조 규칙

- 문서는 한국어 중심으로 작성한다.
- 목적이 분명한 도입부 뒤에 구조화된 본문이 이어져야 한다.
- 가능하면 `## 문서 목적`, `## 관련 문서`, `## 확정 구현 기준` 같은 반복 패턴을 유지한다.
- 상위 섹션은 일관된 번호 체계를 유지한다.

### 권장 패턴

```markdown
# 문서 제목

## 문서 목적

## 관련 문서

## 1. 주요 섹션

## 2. 세부 규칙

## 확정 구현 기준
```

### 안티패턴

- 문서 목적 없이 본문부터 시작하는 경우
- 같은 문서 안에서 번호 섹션과 비번호 섹션을 뒤섞는 경우
- 제목과 본문 예시의 프로젝트 문맥이 서로 다른 경우

---

## 4) 용어, 예시, 설정 정합성

이 저장소는 도메인 용어와 예시 표기가 문서 간 동일해야 한다.

### 리뷰 체크포인트

- 파일 경로, 환경 변수, URL, 명령어 예시가 문서마다 다르게 적히지 않았는가?
- 상태명, 이벤트명, 계약 용어가 문서마다 임의로 바뀌지 않았는가?
- README와 상세 문서 사이의 절차가 충돌하지 않는가?
- 예시가 현재 저장소 기준이 아니라 다른 프로젝트 잔여 문맥을 그대로 복사한 것은 아닌가?

---

## 5) Git / Issue / PR 규칙

이 저장소의 협업 규칙은 `ref/git-convention.md` 같은 기준 문서를 우선한다.

### 브랜치 규칙

- 기본 브랜치는 `main`이다.
- `develop` 브랜치는 사용하지 않는다.
- 이슈 1개당 브랜치 1개를 사용한다.
- 브랜치명은 `{type}/{issue-number}-{description}` 형식을 따른다.
- 브랜치명에는 `#`을 넣지 않는다.

예시:

```text
feat/80-family-detail
fix/82-family-detail-bug
```

### 커밋 규칙

- 커밋 메시지 형식은 `{type}: 작업 내용 (#{issue-number})` 이다.
- 한 커밋에는 한 가지 변경 목적만 담는 것을 권장한다.

### PR 규칙

- PR 제목 형식은 `[#issue-number] 총 작업 내용` 이다.
- PR 본문에는 `Closes #...` 를 포함해야 한다.
- PR 템플릿, 이슈 템플릿, 자동화 라벨 규칙은 서로 충돌하면 안 된다.

### 리뷰 체크포인트

- 템플릿에 다른 조직의 브랜치 규칙이나 Jira 규칙 같은 외부 프로젝트 흔적이 남아 있지 않은가?
- 브랜치 / 커밋 / PR 규칙이 현재 저장소 자동화와 충돌하지 않는가?
- 이슈 타입과 PR 라벨 규칙이 기준 문서와 일치하는가?

---

## 6) 리뷰에서 특히 중요한 실패 유형

다음 항목은 우선적으로 지적한다.

1. **다른 프로젝트 문맥 혼입**
    - 이전 프로젝트명, 다른 조직 규칙, 무관한 도메인 예시가 남아 있는 경우
2. **문서 간 불일치**
    - README, 상세 문서, 템플릿, 자동화 규칙이 서로 다른 기준을 말하는 경우
3. **검증 불가능한 모호한 표현**
    - “적절히”, “상황에 따라”, “필요 시”처럼 기준 없이 쓰인 문장만 있는 경우
4. **보안 부주의**
    - 실제 토큰, 실제 URL, 민감한 설정값이 노출되거나 예시에 포함된 경우

## 7) 리뷰 코멘트 예시

### 좋은 예

- `PR 템플릿에는 GitHub Issue 중심 규칙이 적혀 있는데, 이슈 폼 설명은 다른 브랜치 전략을 안내하고 있어 서로 충돌합니다. 기준 문서를 하나로 맞추고 템플릿 문구도 동일하게 정리하는 편이 안전합니다.`
- `[nit] README에서는 main 기준 PR 흐름을 설명하는데 예시 브랜치명은 issue 번호 없이 작성되어 있습니다. 브랜치 예시를 {type}/{issue-number}-{description} 형식으로 맞추면 더 일관됩니다.`

### 피해야 할 예

- `이상합니다.`
- `그냥 바꾸세요.`
- `프로젝트랑 안 맞는 듯?`

---

## 확정 구현 기준

리뷰는 다음 조건을 모두 만족할 때 통과로 본다.

- 저장소 문맥이 일관되게 유지된다.
- 템플릿, 문서, 자동화 규칙이 서로 맞는다.
- 브랜치 / 커밋 / PR 규칙이 기준 문서와 일치한다.
- 다른 프로젝트의 잔여 문맥이 제거되어 있다.
- 민감한 정보나 실제 비밀값이 포함되지 않는다.
