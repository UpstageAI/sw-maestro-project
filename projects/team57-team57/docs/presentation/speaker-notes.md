## Slide 2 — 서비스 선정 배경 (45s)

**멘트 (필수)**:
소상공인 1인 사장님은 매일 마주하는 리뷰 응대에서 세 가지 문제를 안고 계십니다.
첫째, 시간 부족. 매일 5건에서 15건 리뷰가 쌓이고, 답글은 미루다 일주일이 묵습니다.
둘째, 부정 리뷰의 단어 선택. "환불해드리겠습니다" 같은 *위험 표현* 한 줄이 매장 정책 분쟁이나 법적 책임으로 번지기 쉽습니다.
셋째, 반복되는 불만. "대기 시간 길어요" 가 4주 연속 들어와도 *데이터로* 보이지 않으면 매주 새 리뷰처럼 응대하게 됩니다.
저희는 이 셋을, *리뷰 운영 시간을 30분에서 5분으로* 줄이는 것으로 풀고자 했습니다.

**백업**:
카페·식당만 따져도 전국 5만 곳, 주당 50만 건의 응대 부담입니다. 1인 운영자 비중이 60% 이상이라, *사장님이 검토만 하면 끝* 인 상태로 1차 가공해주는 비서가 시장 가치가 있다고 봤습니다.

**강조**: "30분 → 5분" — 숫자를 천천히. 핵심 슬로건.

**전환**: 그래서 저희가 만든 차별점은 세 가지입니다 →

## Slide 3 — 핵심 가치 (40s)

**멘트 (필수)**:
첫째, *매장 톤 학습*. 사장님이 답글을 수정하시면 저희가 그 차이를 *구조화된 JSON* 으로 자동 추출합니다. 어떤 차원이, 어떤 표현에서 어떤 표현으로 바뀌었는지를 뽑아 다음 답글 prompt 에 주입합니다. 쓸수록 우리 가게답게.
둘째, *다세션 패턴 분석*. 4주치 누적 부정 리뷰를 SQL 로 집계하고, LLM 이 자유롭게 정리해 TOP 3 와 점검 체크리스트를 만듭니다.
셋째, *다층 안전성*. 분류 신뢰도가 낮으면 보수적 답글로 자동 분기하고, 위험 표현은 후처리 사전 치환까지 거칩니다.

**백업**:
세 가지 모두 Memory Store namespace 로 매장별 영속 격리됩니다. 카페 A 의 톤이 식당 B 답글에 끼는 일은 *구조적으로 불가능* 합니다.

**강조**: "쓸수록 우리 가게답게" — 강세 + 한 박자 쉬기. *구조적으로 불가능* 도 강조.

**전환**: 이 세 가치를 실제로 어떤 기능으로 풀었는지 보겠습니다 →

## Slide 4 — 서비스 핵심 기능 (50s)

**멘트 (필수)**:
서비스는 세 가지 시간 축으로 동작합니다.
*일상* 에서는 리뷰 한 건이 들어오면 메인 graph 가 6 노드를 통과해 분류와 답글 초안을 만들고 사장님 수정을 받습니다.
*회고* 에서는 주말에 batch graph 가 4주 누적을 집계해 TOP 3 와 점검 체크리스트를 줍니다. "대기 12회, 가격 5회, 위생 3회" 같은 식으로 *데이터로* 보입니다.
*대화* 에서는 ReAct chat agent 가 "오늘 새 리뷰 3건 분석해줘" 같은 자연어 요청을 5개 tool 로 처리합니다.

**백업**:
세 기능 모두 같은 Memory Store 와 같은 SQLite 를 공유합니다. 일상에서 누적된 데이터가 회고 분석의 입력이 되고, 회고 결과가 다시 채팅으로 조회됩니다.

**강조**: "일상 / 회고 / 대화" — 세 단어 또박또박. 시간 축의 3 단계.

**전환**: 이 세 기능을 한 시스템에 묶기 위해 LangGraph 의 6 가지 surface 를 깊이 있게 활용했습니다 →

## Slide 5 — Agent Workflow 기획 (40s)

**멘트 (필수)**:
왜 LangGraph 인가. 6 가지 표면을 모두 *깊이* 활용했습니다.
Node 와 State reducer 로 trace 가 자동 누적되고, Conditional edge 로 분기가 그래프 시각화에 그대로 노출됩니다.
Cross-thread Memory Store namespace 로 매장별 multi-tenant 가 자연스럽고, bind_tools 로 정통 LLM-driven tool calling 을 구현했습니다.
prebuilt create_react_agent 로 챗 agent 를 5줄에 만들었고, streaming updates 모드로 노드 진행을 UI 사이드바에 ✓ 아이콘으로 노출합니다.

**백업**:
오른쪽 표에 *어디서 보이는지* 까지 적어뒀습니다. 평가위원이 trace 한 번만 펼치면 6 surface 가 다 보이도록 설계했습니다.

**강조**: "6 surface" 와 "깊이 있게" — 평가 포인트.

**전환**: 그럼 실제 graph 구성을 한 슬라이드로 보여드리겠습니다 →

## Slide 6 — Agent Workflow 구성 (60s)

**멘트 (필수)**:
화면에 보이는 다이어그램은 세 개의 graph 를 한 슬라이드에 모은 것입니다.
*왼쪽 메인 graph* 는 load_context, pii_mask, classifier, route_by_sentiment, drafter 5종, memory_save 까지 6 노드.
가운데 분기 다이아몬드는 conditional edge 로, 감정과 신뢰도 두 축으로 *5 갈래* 드래프터 중 하나를 고릅니다. 분류가 실패하거나 비한국어면 *noop drafter* 로 분기해 사장님이 직접 작성하시도록 합니다.
*가운데 batch graph* 는 pattern_aggregator 가 bind_tools 로 SQL tool 을 직접 호출하고 checklist_generator 가 자유 생성합니다.
*오른쪽 chat agent* 는 prebuilt ReAct loop 가 5 개 tool 을 왕복하며 자연어 응답을 만듭니다.
총 노드 9 개, 분기 5 종, tool 6 개로 surface 6 개를 한 번에 시연합니다.

**백업**:
하단 분기 조건표를 보시면 — neg + confidence ≥ 0.7 → apology, < 0.7 → apology_lowconf 의 *보수적 prompt*. LLM 의 단정적 사과를 피하기 위한 안전 장치입니다.

**강조**: "9 / 5 / 6 / 6" — 숫자 명확히. 분량의 깊이 어필.

**전환**: 그럼 실제 시연 흐름을 한 timeline 으로 보여드리겠습니다 →

## Slide 7 — Agent Workflow 시연 + 마무리 (60s)

**멘트 (필수)**:
시연은 네 시나리오를 하나의 흐름으로 묶었습니다.
첫째, 새 리뷰 5건 fetch. 사이드바 노드 진행이 ✓ 로 차오르고 부정 카드가 등장합니다. 신뢰도 0.55 인 케이스는 *apology_lowconf* 로 자동 분기 — 여기서 *Conditional Router* 가 동작합니다.
둘째, 답글의 "미안해요" 를 "죄송합니다" 로 수정 저장하면, 저희가 만든 구조화 JSON 추출이 *사과표현 차원의 선호 변경* 으로 인식해 기존 hint 와 자동 merge — *Memory Store* surface 입니다.
셋째, TOP 3 새로고침을 누르면 batch graph trace 가 llm_decide, sql_tool, llm_summarize 3 단계로 분할 — *Tool calling* 이 그대로 보입니다.
넷째, 우하단 매장 비서에서 "오늘 새 리뷰 3건 분석해줘" 라고 입력하면 *ReAct loop* 가 main graph tool 을 호출하고 자연어로 요약합니다.
이상으로 발표를 마치겠습니다. 감사합니다.

**백업**:
네 시나리오는 각각 *다른 surface* 에 매핑되도록 의도적으로 설계했습니다. 한 번 데모를 보면 LangGraph 6 surface 중 4 개가 시각적으로 확인됩니다. 나머지 두 surface — State reducer 와 Streaming — 은 화면 전체에 ✓ 아이콘과 trace expander 로 *내내* 동작하고 있습니다.

**강조**: 각 시나리오 끝에 surface 이름 — Conditional / Memory / Tool / ReAct. 마지막 "감사합니다" 또박.

**전환**: (QA 모드)
